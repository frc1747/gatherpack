# HBR fork: agent core

The always-loaded digest of [`fork/STRATEGY.md`](STRATEGY.md) for Claude Code sessions. STRATEGY.md is the authority: if the two disagree, follow STRATEGY.md and fix this file. When a situation isn't covered, stop and ask rather than improvising a branch or history change.

## Branches

- `upstream` = GatherPack/gatherpack (read only). `origin` = frc1747/gatherpack (public).
- `main`: exact mirror of `upstream/main`, fast-forward only. Never commit.
- `hbr/platform`: fork-only tooling (`fork/`, `FORK.md`, `bin/fork-*`, `.github/workflows/hbr-*.yml`, sample data, specs, backlog). Never in a feature branch.
- `feature/<name>`: one feature, based on `upstream/main` (or a declared dependency), written to upstream's standards so it can be a PR unchanged.
- `hbr/integration`: generated by `bin/fork-rebuild`. Never commit by hand. Releases are tags `v<upstream>-hbr.<n>` on it.

## Rules

1. Never commit to `main` or `hbr/integration`. Never branch a feature from `hbr/integration` or `hbr/platform`.
2. One feature per branch. A change serving two features is a third branch.
3. Resolve conflicts on feature branches, never during the integration merge.
4. `--force-with-lease`, never `--force`. Never rebase or push a branch behind an open upstream PR unless maintainers ask.
5. Keep `FORK.md` current in the same session as any feature status change.
6. Add, don't edit: prefer new files, seams (Settings.register, HookCatalog, registries), concerns and initializers over editing upstream files. Any upstream file you edit goes in `FORK.md` "Upstream files touched".
7. Confirm behavior in the GatherPack source before assuming a Rails convention or API.
8. Ask before deleting a branch, rewriting a tag, or changing the manifest order.
9. Never modify an upstream migration. Fork migrations are new and reversible. `db/schema.rb` and `Gemfile.lock` are regenerated, never hand-merged.
10. Behavior-changing fork features get a flag, default off.

## Workspace

`~/dev/gatherpack/` holds one worktree per branch: `platform/` (hbr/platform, primary clone), `feature-<name>/`, `integration/`. Create worktrees from `platform/` with `git worktree add ../feature-<name> feature/<name>`. Keep task worktrees inside this folder too (herdr: `--path ~/dev/gatherpack/task-<slug>`), so they load this file and the workspace skills.

## Load on demand

Skills (in `.claude/skills/`, sources in `fork/claude/skills/`) carry the procedures. Use them instead of rereading STRATEGY.md:

- `gp-map`: where things live in the GatherPack code and how its seams work. Read before exploring the code.
- `fork-feature`: start or extend a feature branch (manifest, catalog, sample data, FORK.md, flags, schema hygiene, tests).
- `fork-sync`: the weekly sync and rebuild.
- `fork-release`: cutting and checking a `-hbr.<n>` release.
- `upstream-pr`: issues and PRs to GatherPack/gatherpack.

Agents (in `.claude/agents/`): `gp-test` runs tests/RuboCop and returns only failures; `gp-explore` answers code questions; `implementer` and `reviewer` are tuned for this repo. Hand long test runs and broad code questions to them rather than doing them inline.

## Dispatching parallel work (herd-dispatch)

GatherPack differs from the generic herd-dispatch workflow in three ways:

- Task specs go in `~/dev/gatherpack/tasks/NN-slug.md` (copy `fork/claude/task-template.md`) and are **not committed**: a committed spec would end up in an upstream PR. Workers read them by absolute path.
- Worktrees: `herdr worktree create --cwd ~/dev/gatherpack/platform --path ~/dev/gatherpack/task-NN-slug --branch task/NN-slug --base feature/<name> ...`, so workers load this file and the skills.
- Merge finished task branches into their feature branch (in that feature's worktree), never into `hbr/platform` or `hbr/integration`.
