# HBR fork: agent core

The rules for working in the HBR fork of GatherPack. This file is the authority for rules; [`fork/STRATEGY.md`](STRATEGY.md) explains the reasoning, and skills hold the procedures. When a situation isn't covered, stop and ask rather than improvising a branch or history change.

## Branches

- `upstream` = GatherPack/gatherpack (read only). `origin` = frc1747/gatherpack (public).
- `main`: exact mirror of `upstream/main`, fast-forward only. Never commit.
- `hbr/platform`: fork-only tooling (`fork/`, `FORK.md`, `bin/fork-*`, `.github/workflows/hbr-*.yml`, sample data, specs, backlog, pitches). Never in a feature branch.
- `feature/<name>`: one feature, based on `upstream/main` (or a declared dependency), written to upstream's standards so it can be a PR unchanged.
- `hbr/integration`: generated by `bin/fork-rebuild`. Never commit by hand. Releases are tags `v<upstream>-hbr.<n>` on it.

## Rules

1. Never commit to `main` or `hbr/integration`. Never branch a feature from `hbr/integration` or `hbr/platform`.
2. One feature per branch. A change serving two features is a third branch. Deliberate exception: `feature/checklists-connectors` and `feature/mcp-checklists-intake` group thin connector code.
3. Resolve conflicts on feature branches, never during the integration merge. Don't merge a core branch into every dependent after each change: fix dependents once at sync and test the combined build.
4. `--force-with-lease`, never `--force`. Never rebase or push a branch behind an open upstream PR unless maintainers ask.
5. Keep `FORK.md` current in the same session as any feature status change or release.
6. Add, don't edit: prefer new files, seams (`Settings.register`, `HookCatalog`, registries), concerns and initializers over editing upstream files. Any upstream file you edit goes in `FORK.md` "Upstream files touched".
7. Confirm behavior in the GatherPack source before assuming a Rails convention or API.
8. Ask before deleting a branch, rewriting a tag, or changing the manifest order.
9. Never modify an upstream migration. Fork migrations are new and reversible. `db/schema.rb` and `Gemfile.lock` are regenerated, never hand-merged.
10. Behavior-changing fork features get a flag, default off.
11. Docs, specs, pitches, backlog, skills and `FORK.md` are pushed to `hbr/platform` directly. Scripts, CI and the manifest order need the owner's OK first.
12. Each fact lives in one place: rules here, reasoning in STRATEGY.md, procedures in skills, product decisions in specs. Change the one place, not a copy.

## Workspace

`~/dev/gatherpack/` holds one worktree per branch: `platform/` (hbr/platform, primary clone), `feature-<name>/`, `integration/`, plus `tasks/` (task briefs, never committed). Create worktrees from `platform/` with `git worktree add ../feature-<name> feature/<name>`, then link the skills in (Claude Code reads them at the git root): `mkdir -p ../feature-<name>/.claude && ln -sfn ../../.claude/skills ../feature-<name>/.claude/skills && ln -sfn ../../.claude/agents ../feature-<name>/.claude/agents` (git-excluded). Task worktrees go in this folder too (`task-NNN-slug`). Remove a worktree once its feature is retired or its task merged.

## Load on demand

Skills (sources in `fork/claude/skills/`, linked into `~/dev/gatherpack/.claude/skills/`):

- `gp-map`: where things live in the code and how its seams work. Read before exploring.
- `fork-feature`: start or extend a feature branch (manifest, catalog, sample data, FORK.md, flags, schema hygiene, tests).
- `fork-spec`: writing specs, pitches, backlog items and task briefs; screen design and copy conventions.
- `fork-sync`: the weekly sync and rebuild.
- `fork-release`: cutting and checking a `-hbr.<n>` release.
- `upstream-pr`: issues and PRs to GatherPack/gatherpack.

Agents (`fork/claude/agents/`): `gp-test` runs tests/RuboCop and returns only failures; `gp-explore` answers code questions; `implementer` and `reviewer` are tuned for this repo. Hand long test runs and broad code questions to them. Parallel workers follow [`fork/claude/worker-rules.md`](claude/worker-rules.md); the lead workflow is the workspace's local `herd-lead` skill. Task worktrees are created from `platform/` on `task/NNN-slug` off the feature branch, and finished task branches merge into their feature branch (in that feature's worktree), never into `hbr/platform` or `hbr/integration`.
